# 最新メッセージによる確定ラップ表示

2026-10-23のdelta-vega-v2のMQTT仕様と実装に合わせ、IoTルール・取得API・ピット画面を更新した。画面は最新の1メッセージから、現在値と全確定ラップを表示する。周回遷移の検出、受信履歴からの逆算、過去に取得したラップの補完は行わない。

## 確認した送信側の実装

delta-vega-v2の作業ツリーにある以下を確認した。この確認時点では送信側の変更は未コミットで、deneb側からは編集していない。

- `lib/vega_core/src/domain/race.cpp` / `types.h`：計測ドメインで自動・手動LAPと最終周の時間を確定し、固定長100件の配列で保持する。取消でクリアし、完走後は保持する。
- `lib/vega_core/src/application/telemetry_json.cpp` / `.h`：既存項目に配列を追加し、100件を含むJSONの容量を確保する。

履歴の確定をドメインへ置き、最新スナップショットに全件を含める方針は、受信漏れや途中からの閲覧に対応できるため妥当と判断した。FreeRTOSへ値としてコピーできる固定長配列を使い、通信待ちを画面へ持ち込まない構成も確認した。送信側のネイティブ試験・実機試験の記録は同リポジトリの仕様書にある。deneb側では送信側の試験を再実行しておらず、実際のAWS取り込み・通信断を含む結合確認は別途必要。

## メッセージと状態

`completed_lap_times_ms`は、1周目から順に並んだ区間タイム（整数、ミリ秒）の配列。累積通過時刻ではない。例は共通テストデータ`tests/fixtures/mqtt-completed-laps.json`に保存している。

```json
{
  "lap_number": 3,
  "total_time_ms": 765000,
  "lap_time_ms": 45000,
  "completed_lap_times_ms": [362000, 358000]
}
```

この例では1周目06:02、2周目05:58、3周目00:45。過去の受信記録がなくても表示できる。

| 状態 | `lap_number` | 配列 | カウンターとの関係 |
| --- | --- | --- | --- |
| 初期・取消後の待機 | 0 | `[]` | 経過・現在ラップとも0 |
| 計測中（開始直後を含む） | 1〜100 | 要素数は周回番号−1 | 配列合計＋現在ラップ＝経過時間 |
| 完走 | 1〜100 | 要素数は周回番号 | 配列合計＝経過時間、最終要素＝現在ラップ |
| 旧形式 | 0〜100 | 項目なし / APIでは`null` | 確定ラップ未取得、完走未確認 |

0ミリ秒の確定ラップも有効。手動LAP直後の手動ゴールなどで発生し得るため欠測扱いにしない。配列の型、最大100件、非負整数、周回番号・合計との整合性をAPIと画面で検証する。数値はブラウザで正確に扱える0〜`2^53−1`に制限する。送信側の64bit整数全域をブラウザへ丸めて表示することはしない。

取消・再開始・再接続では、その時点の最新配列へ丸ごと置き換える。履歴APIが遅れて返ってもラップ一覧を上書きしない。旧データは「確定ラップ未取得（旧形式）」と表示し、明示的な空配列と区別する。

完走と待機はイベント時に送られる状態で、周期送信されるとは限らない。完走後も受信時刻を表示し、10秒経過だけで走行中の「更新停止」へ変えない。走行中の更新停止判定、通信取得エラーの表示は継続する。QoS 0・retainなしのため完走メッセージ自体が未受信の場合は、受信側だけで完走を確定できない。再接続時には送信側が保持している最新状態を再送する。

`timestamp_ms`は車両の起動後時間で、再送時も元の状態取得時刻。受信順・鮮度・期間選択にはAWSの`received_at_ms`を使う。

## 受信・保存・API

CDK管理の専用IoTルールのSELECTに`completed_lap_times_ms`を追加した。DynamoDBv2アクションはSELECT結果をそのまま項目として書き込むため、配列用のキー・GSI追加やテーブル作り直しは不要。[AWSのDynamoDBv2アクション仕様](https://docs.aws.amazon.com/iot/latest/developerguide/dynamodb-v2-rule-action.html)と[SELECTの仕様](https://docs.aws.amazon.com/iot/latest/developerguide/iot-sql-select.html)を参照。

- `/api/telemetry/latest`：従来どおり逆順Query・Limit 1。`latest.completed_lap_times_ms`に全確定ラップを返す。欠落は`null`。
- `/api/telemetry/history`：グラフ・過去の期間・CSV用に維持する。各サンプルにも配列を返す。過去結果も選択した走行候補の最後のサンプルだけからラップを表示する。
- `/api/telemetry/laps`：互換用に維持し、対象期間の最新1件だけをQueryする。`laps`は`{lap, time_ms, source: "device"}`。`lap_times_available`で新項目の有無、`finish_confirmed`で最終周を含むことを示す。履歴走査やページ送りはしない。`truncated`は`false`。

画面はラップAPIを呼ばず最新APIから一覧を表示する。履歴の取得成否は現在値・ラップ表示を妨げない。過去の走行候補の区切りと速度グラフの履歴は引き続き受信カウンターから推定する。MQTTに計測IDがないため、全く同じカウンターで始まる別計測の識別や厳密な走行単位の検索は保証できない。

## コースと画面

タイムの表示・状態判定は7周固定を外し、1〜100周に対応する。完走前の予定周回数はMQTTにないため、`/7`などの分母や未来の周回は表示しない。100件はラップ表内でスクロールでき、ダッシュボード全体の配置は維持する。

同梱地図と戦略JSONは引き続きもてぎ用。MQTTにコースIDがないため、別コースの地図や戦略へ自動で切り替えることはできない。GPS位置は同梱経路群の最寄りへ投影し、60mを超える場合はコース外表示にする。読み込んだ戦略に現在周回がない場合、1周目を代用せずその周回の戦略がないことを表示する。別コースのタイムも受け取れるが、その地図を表示するにはコース識別と地図の追加が必要。

## 反映手順（ユーザーがDev Containerで実行）

[Step 3のデプロイ手順](step3-deployment.md)に沿って、ブランチ`codex/mqtt-completed-laps`を取得し、テスト・オフラインsynth後にdiff・deployする。更新対象は静的コンテンツ、Lambdaコード、専用IoTルールのSQL。リソースの追加・置換、テーブルの削除・移行は不要。CDK管理のルールを更新するため、同じルールをコンソールで手動編集する必要はない。別途使っている旧ルールにはこの更新を加えない。

古い保存済みレコードへ新項目は遡って追加されない。新しい送信側のファームウェアと更新済みIoTルールを使って、新しいサンプルを送信した後に確認する。送信側と受信側をどちらから更新しても、移行中の旧形式は未取得と表示される。

```sh
uv run --locked python scripts/check_telemetry.py --outputs cdk-outputs.dev.json --profile delta-deneb-login --require-data --require-completed-laps
```

この確認はトークンを表示しない。`--require-completed-laps`は配列が欠落する旧ルール・旧ファームウェアを検出する。開始前の`[]`でも新形式の取り込み確認にはなる。ラップ・完走そのものの受け入れ試験は以下を行う。

1. 途中の3周目から共有リンクを新規に開き、過去2周の車両確定タイムを確認する。
2. 自動・手動LAP、複数周の通信断後の復帰で、一覧が車載表示と一致することを確認する。
3. 自動・手動完走後に最終周が1回だけ入り、10秒を超えても完走表示とタイムが保たれることを確認する。
4. 取消で待機・空配列となり、再開始に前計測のタイムが混ざらないことを確認する。
5. 通信断中の完走から復帰したときに、全結果を受信することを確認する。
6. 周回数の異なるコースと100周で一覧・CSVを確認する。地図の対応範囲は上記のとおり。

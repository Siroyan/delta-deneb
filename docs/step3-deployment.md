# Step 3: ピット画面を実データAPIへ接続する

承認済みの画面配置を維持し、Step 2の取得APIへ接続する。共有リンク、通信断からの復帰、過去の期間の選択に対応した。現在の画面はライブ表示に統一し、ラップ分析と走行進捗パネルを削除済み。過去の期間は引き続き選べる。delta-vegaの実機を含む確認は、起動できるようになってから行う。

すべてのコマンドはDev Container内の`/workspaces/delta-deneb`で実行する。AWSへのログイン・diff・deploy・Secretの取得はユーザー自身が行う。認証情報をチャットへ渡す必要はない。

## 1. コードと依存関係を更新する

```sh
cd /workspaces/delta-deneb
git fetch origin
git switch codex/mqtt-completed-laps
git pull --ff-only
uv sync --locked
npm ci
npm test
npm run test:infra
npm run synth:offline
```

手元に未コミットの変更がある場合は、内容を確認してからブランチを切り替える。このブランチはStep 1・Step 2を含む。Dev Containerのポート転送設定に8081番を追加したため、必要に応じて「Dev Containers: Rebuild Container」を実行する。

## 2. 実機なしで画面を確認する

```sh
npm run preview:api
```

VS Codeの「ポート」で8081番を開き、URLを`http://127.0.0.1:8081/#token=local-preview`にする。転送先ポートが異なる場合はその番号を使う。`local-preview`はローカル専用のダミー値で、AWSでは使えない。

このサーバーはループバックだけで待ち受け、AWSへ接続せず、静的画面と模擬HTTP APIを配信する。画面側は本番と同じAPI取得処理を通る。最新値・履歴のページ分割・車両確定ラップ・複数走行候補を確認できる。停止は`Ctrl+C`。

状態を変えるには、次のURLを別タブで開く。元の画面へ戻ると取得が再開する。

| 確認する状態 | ローカル専用URL |
| --- | --- |
| 通常・復旧 | `http://127.0.0.1:8081/__preview/state?scenario=live` |
| 更新停止 | `http://127.0.0.1:8081/__preview/state?scenario=stale` |
| GPS欠測 | `http://127.0.0.1:8081/__preview/state?scenario=gps-missing` |
| データなし | `http://127.0.0.1:8081/__preview/state?scenario=empty` |
| APIエラー | `http://127.0.0.1:8081/__preview/state?scenario=error` |
| リンク無効 | `http://127.0.0.1:8081/__preview/state?scenario=unauthorized` |

APIエラーから通常へ戻すと自動で回復する。リンク無効で401を受けた場合は、自動取得を止める。サーバーを通常へ戻し、共有リンクを再読み込みして復帰を確認する。更新停止は受信時刻を固定し、画面の値が古いと分かる表示になる。データなしの初期表示は、`empty`へ変更してから画面を再読み込みする。既に取得済みの値は、一時的に最新APIが空になっても保持する。実運用で起きる送信遅延や並べ替えの完全な再現ではない。

Lap 2→3の回帰確認は、同じ画面を開いたまま以下の順に行う（再読み込みしても最新メッセージだけで一覧を表示する）。

1. 別タブで`/__preview/state?scenario=lap-2`を開き、元の画面でLap 2・Lap 1の05:00を確認する。
2. 別タブで`/__preview/state?scenario=lap-3-partial`を開く。履歴は最新1件だけを返す。最新値の配列には全確定ラップを含める。
3. 元の画面がLap 3になっても、Lap 1の05:00とLap 2の05:30を表示できることを確認する。
4. 確認後は`/__preview/state?scenario=live`で通常へ戻し、画面を再読み込みする。

履歴の遅延時も最新値とラップ一覧が更新されることは、次で確認する。

```sh
npm run preview:api -- --details-delay 8
```

履歴・ラップの応答だけをそれぞれ8秒遅らせる。画面を開くと最新の速度・GPS・経過時間を先に表示し、履歴を待っている間も3秒ごとの最新値取得を続ける。`--details-delay 12`では10秒のリクエスト制限を超えるため、履歴側の再試行と最新値の更新を同時に確認できる。指定範囲は0〜30秒。AWSへは接続しない。

従来のブラウザ内デモも残している。

```sh
npm run preview
```

8080番の`http://127.0.0.1:8080/?demo=1`を開く。右上のシナリオ選択で、従来の画面・戦略表示を確認できる。`?demo=1`がない通常URLは実API用で、トークンがなければデータを表示しない。実APIのエラーやデータなしを模擬走行に置き換えることもない。

## 3. AWS上の画面を更新する

**Step 2を未デプロイの場合は、先に[Step 2の手順](step2-deployment.md)で配布基盤の権限更新とアプリの更新を行う。** 実機が停止していてもAPIの疎通確認までは進められる。`--require-data`を使う取り込み確認は後回しにする。

Step 2をデプロイ済みなら、新しいAWSリソースや権限を追加せず、同じアプリスタックを更新する。確定ラップ対応では専用IoTルールのSELECTにも`completed_lap_times_ms`を追加する。DynamoDBの作り直し・移行やコンソールでの手動ルール変更は不要。

```sh
aws login --profile delta-deneb-login --remote
aws sts get-caller-identity --profile delta-deneb-login
npm run cdk -- diff DeltaDenebDev --profile delta-deneb-login
```

デプロイ先と専用IAMユーザーを確認する。Step 2からの差分には静的コンテンツの配布用アセット、Lambdaコード、専用IoTルールのSQL更新が含まれる。意図しないリソース削除・置換があればデプロイを止めて確認する。

```sh
npm run cdk -- deploy DeltaDenebDev --profile delta-deneb-login --outputs-file cdk-outputs.dev.json
uv run --locked python scripts/check_deployment.py --outputs cdk-outputs.dev.json --step 2
uv run --locked python scripts/check_telemetry.py --outputs cdk-outputs.dev.json --profile delta-deneb-login
```

ヘルスチェックの`step: 2`はAPI契約の段階を示すため、画面接続後もそのまま。最後の確認が`WAIT No stored telemetry yet; ingestion is not verified`の場合は、APIには接続できているが取り込みは未確認。新規データがなくてもデプロイ失敗ではない。

CloudFrontの`SiteUrl`は引き続き同じものを使う。配信の反映後、ブラウザを再読み込みする。DynamoDBとSecretを保持する既存設定も継続する。更新のためにスタックを削除しない。

## 4. 閲覧用の共有リンクを作る

ユーザー自身のターミナルで実行する。

```sh
uv run --locked python scripts/share_link.py --outputs cdk-outputs.dev.json --profile delta-deneb-login
```

出力される`https://……cloudfront.net/#token=……`をピットのメンバーへ共有する。スクリプトは既存のAWS CLI用Profileで閲覧用Secretを読み取り、リンクを一度表示する。ファイルには保存しない。`--profile`を省略した場合は、手元にあるトークンを非表示で入力できる。

**このリンク自体が閲覧権限を持つ。** ターミナルの出力やコピーしたリンクを、公開Issue・リポジトリ・チャットへ貼らない。閲覧者はAWSにログインする必要がない。

画面はフラグメントからトークンを読み、APIリクエストの`X-Deneb-Token`ヘッダーに設定する。クエリ文字列やブラウザのlocalStorage・sessionStorageへは保存しない。コピーと再読み込みのため、アドレス欄のフラグメントは保持する。参照元情報は送信せず、別オリジンへのAPIリダイレクトも追わない。

トークンなしでは「共有リンクが必要」、不一致では「リンクを確認」と表示する。401では表示中のデータを消して自動取得を止める。管理者がトークンを変更した場合は新しいリンクを作成し、メンバーに開き直してもらう。Secret更新後のAPIキャッシュは最大約60秒。[Step 2のトークン更新](step2-deployment.md#保持トークン更新費用)を参照。更新する値は英数字・`-`・`_`の1〜256文字にする。初期値は48文字の英数字。

## 5. 画面の使い方とデータの意味

### 最新の走行

- 最新APIの取得完了から3秒後に最新値を再取得する。速度履歴の取得完了は待たず、最新の速度・GPS・周回・確定ラップを先に表示する。1リクエストは10秒で打ち切る。通信エラー時は最後に取得できた値と注意表示を残し、3・6・12・24・30秒の間隔で再試行する。サーバーが待機を指定した場合は最大60秒まで尊重する。
- 走行中に受信から10秒を超えると「更新停止」。待機・完走の通知は周期送信を前提にしないため、経過時間だけで更新停止へ変えない。APIへの問い合わせ成功だけではLIVEにしない。表示する受信時刻はAWSの`received_at_ms`で、機器の起動後時間`timestamp_ms`を日時に変換しない。鮮度判定にはAPIの時刻とブラウザの時刻の差を補正する。
- タブを隠すと最新値・履歴の取得を中断し、戻ると再開する。過去表示や共有リンクの切り替え時も中断する。過去の応答で表示を上書きしない。GPSが欠測・コースから60m超の場合はマーカーを消し、速度とタイムの更新を続ける。
- 履歴は5秒重ねて差分取得し、`sample_id`で重複を除く。1回の更新で最大3ページを取り、残りは次回へ継続する。速度履歴の取得は最新値と別の処理で、同時に1件だけ実行する。取得が遅い場合や失敗した場合も最新値のポーリングを続け、該当処理を待機後に再試行する。遅れて届いた結果は、その時点の最新値に履歴を補う形で表示する。
- 確定ラップは最新メッセージの配列を毎回表示する。ラップAPIや周回遷移の検出は不要。速度履歴は最大10,000件を保持し、上限や取得失敗はグラフ付近に表示する。ラップの補完・保持は行わず、取消や再開始で最新の空配列へ置き換える。

### 過去の期間

右上を「過去の期間」にし、日本時間で開始・終了を指定して「記録を表示」を押す。最大2時間の期間を選べる。期間は直近2時間に限定されず、保存済みであれば以前の日付も選べる。

機器の起動後時間・経過時間・周回数が減った地点で走行候補を分ける。複数あるときは「走行候補」で切り替える。正式な走行IDがないため、機器の補正や送信順の入れ替わりでも分かれる場合がある。過去の表示中は自動取得しない。

履歴は最大20ページ・10,000件。打ち切り時は「履歴は一部のみ」と表示するので、期間を狭めて取得し直す。「CSVを保存」は選択中の走行の取得済み記録だけを書き出す。テーブル全体のエクスポートではない。

### 推定と確定

ラップタイムは`completed_lap_times_ms`の車両確定値を使う。最終周を含む配列で完走を確認する。項目のない旧形式は確定タイム未取得とし、逆算や過去の取得値で埋めない。0msを含む1〜100周に対応する。予定周回数はMQTTにないため分母は表示しない。契約と送信側の確認結果は[確定ラップ表示の仕様](mqtt-completed-laps.md)を参照。

走行距離・進捗・ゴール予測は表示しない。目標38:30は仮の表示設定で、実際の制限時間ではない。戦略JSONの読み込み・保存・ON/OFF照合はこれまでどおり使える。戦略はブラウザ内だけで扱い、車両やAWSへ送らない。

## 6. 実機が使えるようになったら行う確認

1. delta-vegaを既存IoT Coreへ接続し、デプロイ後のデータを送信する。
2. `scripts/check_telemetry.py`を上記と同じ引数に`--require-data --require-completed-laps`を追加して実行し、取り込みを確認する。
3. 共有リンクで速度・平均速度・周回・経過・GPS・受信時刻を車載表示と照合する。更新停止から再接続したときの復帰も見る。
4. 周回境界、機器再起動、走行リセットを確認し、最新の確定ラップ配列が車載表示と一致し、取消・再開始で前の走行と混ざらないことを見る。
5. 実際の閲覧端末と人数で遅延・読取量を確認し、更新周期や履歴上限を調整する。通信断中に完走した後の復帰と、完走後10秒を超えた表示も確認する。

## 開発側の検証範囲

AWSの認証・デプロイ・実テーブル操作は行わない。Dev ContainerのテストでAPI取得・トークン・時刻・再試行・ページ分割・取消・走行区切りを確認し、ローカル模擬HTTP APIからブラウザ画面までを検証する。これらは実機からAWSへの取り込み成功や、本番AWS上の権限評価を示すものではない。

2026-10-19のUI簡素化とラップ修正では、JavaScript 38件・Python 112件が成功した。Lap 2→3の部分応答・履歴保持上限・走行リセットと、Lap 1が取得範囲外のAPI応答を検証した。

2026-10-23のPRレビュー対応では、最新APIの応答を履歴・ラップ待ちから分離した。JavaScript 45件・Python 113件とオフラインsynthが成功した。履歴・ラップの遅延、同時呼び出しの抑制、中断と再開、走行リセット後の遅延応答の破棄、ラップ遷移の保持を検証した。

2026-10-23の確定ラップ対応では、送信側の新仕様を確認し、IoTルール・API・画面を変更した。最新1件だけからの一覧、履歴障害・遅延、旧形式、取消・再開始・完走・0ms・100周をオフラインで検証する。最新API以外が失敗する模擬確認は`npm run preview:api -- --scenario latest-only`で行える。`waiting`、`started`、`finished`、`zero-final`、`lap-100`、`legacy`も状態切替URLで選べる。
